## 1. Prerequisites

- **Node.js 18 or newer.** No other runtime is required.
- A text editor (any editor works — VS Code, Sublime Text, Notepad++, etc.).
- A modern browser for visual testing.
- Optional: a screen reader such as NVDA (Windows, free), JAWS (Windows), VoiceOver (macOS/iOS, built-in), or Orca (Linux, free) for accessibility testing.

## 2. Local setup

```bash
# Clone the repository
git clone https://github.com/sagan-edu/sagan.git
cd sagan

# No npm install needed — there are no runtime dependencies.

# Run quality checks
npm test

# Build the static production site into dist/
npm run build

# Serve the built site locally at http://localhost:4173
npm start
```

Open your browser to `http://localhost:4173` after running `npm start`.

## 4. Running tests and building

```bash
# Run all automated checks (must pass before submitting a PR)
npm test

# Build the production site
npm run build

# Preview the built site
npm start
```

`npm test` runs `scripts/check.js`, which verifies structural, accessibility, and link-correctness requirements. All checks must pass in your pull request.

## 5. How to contribute

### Good first contributions

- Improve a lesson for clarity while preserving scientific accuracy.
- Add an accessible text description for a chart or diagram.
- Test keyboard-only and screen-reader navigation and report barriers using the accessibility issue template.
- Add a short glossary entry or formative knowledge-check question.
- Propose a public dataset with full provenance (source, identifier, license, units, caveats).
- Improve translations, responsive layout, or sonification mapping explanations.
- Fix a broken link or update outdated information.

### Workflow

1. **Open an issue first** for new chapters, large rewrites, or anything that changes the curriculum structure. This avoids duplicated effort.
2. **Fork the repository** and create a branch with a descriptive name: `fix/footer-links`, `lesson/variable-stars`, `a11y/keyboard-chart`.
3. **Make your changes** following the guidelines below.
4. **Run `npm test` and `npm run build`** and fix any failures before opening a PR.
5. **Open a pull request** using the PR template. Describe what you changed, why, and what accessibility testing you did.

### Before submitting

- Keep synthetic examples labelled as synthetic everywhere they appear.
- Cite reliable sources for all astronomy claims.
- Do not commit private, licensed, or unreviewed astronomical data.
- Describe accessibility checks and known limitations in the pull request description.
- The platform is an early prototype. Do not imply that planned integrations or the proposed GAN model are already implemented.

## 6. Lesson authoring guide

New lessons should follow the structure in [`curriculum/LESSON_TEMPLATE.md`](curriculum/LESSON_TEMPLATE.md). Here is a summary of the key principles:

### Language and tone

- Write for a broad age range (roughly 10 and up) unless the chapter explicitly targets a narrower audience.
- Use short sentences (aim for under 25 words each).
- Define every technical term in plain language on first use.
- Prefer active voice and concrete examples over abstract statements.
- Avoid idioms that may not translate well.

### Content structure

Each chapter should include:

1. **Title** — short and specific, no jargon.
2. **Intro** (2–4 sentences) — shown as the "lead" paragraph below the chapter title.
3. **Body sections** — 3–5 `<h3>`-headed sections with explanatory text, lists, and at least one callout box.
4. **Callout box** — highlight the single most important concept or a "try it" prompt.
5. **Activity** — one brief thing the learner can do without special equipment.
6. **Knowledge check** — 2–4 questions testing understanding, not just recall.

### Accuracy and care

- Report scientific claims with appropriate certainty. Use "may", "suggests", "is consistent with" rather than "proves" or "is".
- Distinguish between what has been observed and what is inferred.
- Note when a detection method has known limitations or selection effects.
- Label all synthetic data as synthetic. Do not present fabricated data as real.

## 7. Data provenance requirements

If your lesson references real astronomical data (even just citing a value from a paper), record:

| Field | What to document |
|---|---|
| Mission / instrument | e.g. "Kepler Space Telescope / photometer" |
| Archive | e.g. "NASA Exoplanet Archive", "MAST" |
| Dataset identifier | e.g. a KIC number, DOI, or URL to the specific dataset |
| Time span | Start and end dates of the observations used |
| Units | Flux units, time system (e.g. BJD-TDB), magnitude system |
| Processing level / pipeline | e.g. "PDC-SAP flux from Kepler pipeline v9.3" |
| Access date | When you retrieved the data |
| Known caveats | Gaps, systematics, contamination, etc. |
| License / terms of use | Check the archive's terms; NASA public-domain data has different terms than ESA or private surveys |
| Attribution statement | The exact credit line required by the data provider |

Keep all real data in clearly labelled, separately tracked files. Do not mix real observations with synthetic teaching data in the same figure or table without a clear label.

## 8. Accessibility checklist

Complete before submitting any PR that changes visible content or interactive behaviour:

- [ ] All images, charts, and visualisations have a text description in the lesson body.
- [ ] The text description communicates the chart's meaning, not just its appearance.
- [ ] New interactive elements are keyboard-operable (Tab, Enter, Space, arrow keys where applicable).
- [ ] New interactive elements have visible focus styles.
- [ ] New interactive elements have meaningful labels (`aria-label`, `<label>`, or visible text).
- [ ] Dynamic content updates are announced (use `aria-live` regions or `role="status"`).
- [ ] Colour is not the only way information is conveyed.
- [ ] The page still makes sense with high-contrast mode enabled.
- [ ] The page was tested at 200% browser zoom without loss of content.
- [ ] The page was tested with keyboard-only navigation.
- [ ] If you have access to a screen reader, test the main flow and note any issues.
